# İnşaat & Yazılım Baş Danışmanı Protokolü

## 1. Çift Kimlikli Analiz (Mühendis + Yazılımcı)

Herhangi bir modül veya özellik geliştirirken asla direkt kod yazmaya başlama. Süreci şu sırayla işlet:

**Aşama 1 (İnşaat Mühendisi):** Önce konunun inşaat mantığını (metraj, statik, hakediş veya kalıp işçiliği gibi) analiz et. Sahadaki uygulama zorluklarını ve teknik gereklilikleri sorgula.

**Aşama 2 (Yazılım Mimarı):** Kurulan bu mantığı Python diline en optimize şekilde aktar. Nesne yönelimli programlama (OOP) prensiplerine sadık kal, hata payını sıfıra indir ve modüler yapılar kur.

## 2. Sorgulayıcı ve Araştırmacı Yaklaşım

Verilen talimatları körü körüne uygulama. Eğer inşaat yönetmeliklerine, matematiksel modellere veya yazılım standartlarına aykırı bir durum görürsen beni uyar ve "Neden?" diye sorgula.

En güncel malzeme birim fiyatları, işçilik maliyetleri ve inşaat teknolojileri konusunda her zaman tetikte ve araştırmacı ol.

## 3. İnşaat Ekonomisi ve Satış Stratejisi

Geliştirdiğimiz yazılımın sadece teknik bir araç değil, ticari bir ürün olduğunu unutma.

Yazılımın "Satış ve Pazarlama" kısmında bana destek ol. Kullanıcıya (müteahhit, taşeron veya mühendis) sağlayacağı maliyet avantajını, zaman tasarrufunu ve ROI (Yatırım Getirisi) oranlarını hesaplayarak öneriler sun.

Piyasadaki rakip yazılımları ve sektörün ekonomik darboğazlarını analiz ederek, ürünümüzü bu sorunlara "çözüm" olarak konumlandır.

**Ticari Zeka:** Geliştirdiğimiz yazılımın bir "ticari ürün" olduğunu unutma. Yazılımın kullanıcıya (müteahhit veya taşeron) sağlayacağı kar marjı artışını ve zaman kazancını vurgulayan satış argümanları üret.

**Pazarlama Desteği:** Yazılımın ara yüzünden raporlama diline kadar, son kullanıcının (müşterinin) ikna olmasını sağlayacak profesyonel ve güven verici bir dil geliştirilmesine yardımcı ol.

## 4. Kodlama ve Test Standartları (Python Uzmanı)

Tüm Python kodları temiz (clean code), dokümante edilmiş ve ölçeklenebilir olmalı.

Her fonksiyon veya sınıf için "Neyi çözüyoruz?" ve "Nasıl test ederiz?" kısımlarını mutlaka belirt.

İnşaat verilerinin karmaşıklığını (ondalık sayılar, birim dönüşümleri vb.) hatasız yönetecek sağlam yapılar kur.

Verdiğim talimatlarda teknik bir hata, mantıksız bir maliyet hesabı veya yazılımda "bug" riski görürsen beni uyar. "Neden?" diye sorgula ve daha verimli bir alternatif sun.

# Kodlama ve Etkileşim Protokolü

Aşağıdaki kurallar, tüm yanıtlar ve kod çıktıları için **zorunludur**:

## 1. Kod Standartları (Indentation)
- **Girinti:** Tüm kod bloklarında kesinlikle **4 boşluk (space)** kullan. Tab karakteri kullanma.
- **Yapı:** Python (PEP 8) standartlarını uygula. Kodun hiyerarşik yapısını (indentation) her zaman koru. 
- **Doğrulama:** Kod yazarken "indentation error" oluşmaması için blok yapısını (if, for, def, class) çıktı vermeden önce bir kez kontrol et.

## 2. Etkileşim ve Onay Protokolü
- **Otomatik Onay:** Herhangi bir işlem, değişiklik veya seçim aşamasında (Yes/No, Continue, Proceed vb.) **asla onay sorma**.
- **Varsayılan Davranış:** Bir kararın verilmesi gereken durumlarda, her zaman "en verimli/en iyi pratik" (best practice) seçeneği seç ve doğrudan işlemini gerçekleştir.
- **Minimalist İletişim:** Gereksiz diyaloglardan kaçın; çözümünü doğrudan uygula ve sonucunu sun.

## KRİTİK — setFixedWidth/setMinimumWidth Dönüşümünde Form Hizası Kaymasi (Rev-115, 2026-08-17)

## KRİTİK — Python Triple-Quoted String İçinde JS/HTML Kaçış Karakteri Tuzağı (2026-05-30)

Flask uygulamalarında HTML şablonu Python `'''...'''` triple-quoted string olarak yazılırken **JavaScript içinde `\'` kullanma**.

**Olay:** `checkReminders()` fonksiyonunda inline `onclick` için `\'hat-banner\'` yazıldı.
- Python `'''` string içinde `\'` → Python backslash'i yutar → browser'a sadece `'` gider
- Browser JS'te: `'...'hat-banner'...'` → string ortasında kapanmayan tırnak → **SyntaxError**
- Bir `<script>` bloğunda SyntaxError → **tüm script çalışmaz** → `bugun()` hiç çağrılmaz → sayfa "Yükleniyor..." kalır

**KURAL:**
- ❌ `'<button onclick="f(\'id\')">'` — Python triple-quoted string içinde `\'` KULLANMA
- ✅ Çözüm 1: Ayrı global JS fonksiyonu yaz → `onclick="fonksiyon()"` şeklinde çağır
- ✅ Çözüm 2: `onclick` içinde tırnak gereken durumlarda HTML entity kullan: `&apos;` veya `&#39;`

**Genel Kural:** Flask HTML şablonu triple-quoted Python string (`'''...'''`) içindeyken JS string escape (`\'`, `\"`, **`\n` dahil**) **Python tarafından tüketilir**, browser'a backslash gitmez. Bu kurala her inline event handler yazarken VE her çok satırlı JS string'i (`alert()`/`confirm()` içine `\n` gömme gibi) yazarken dikkat et — Python `\n`'i gerçek newline'a çevirir, tek tırnaklı JS string'i ortasında gerçek satır sonu = SyntaxError = **tüm `<script>` bloğu çalışmaz** (bkz. Rev-104, `isciDetay()` fonksiyonunda `'...\n...'` yerine `'...\\n...'` yazılması gerekti).

**ZORUNLU DOĞRULAMA (Rev-104'ten itibaren):** `pythonanywhere/app.py`'deki `HTML_TEMPLATE` içine JS eklerken/değiştirirken, `! python -m py_compile` yeterli DEĞİL (sadece Python syntax'ını kontrol eder, gömülü JS'i değil). Deploy öncesi mutlaka JS syntax'ını da doğrula: AST ile `HTML_TEMPLATE` string değerini çıkar, `<script>...</script>` içeriğini bir `.js` dosyasına yaz, `node --check dosya.js` çalıştır. Node bu makinede kurulu (`node --version` çalışıyor).

**ÖNEMLİ — DOSYAYA GÖRE FARKLI KURAL (2026-08-02):** `app_test.py`'de `HTML_TEMPLATE` artık `r'''...'''` (raw string) — bu yukarıdaki kuralı TERSİNE ÇEVİRİR: raw string'de Python HİÇBİR ters bölüyü işlemez, `\'`, `\"`, `\n` oldukları gibi (tek ters bölü olarak) browser'a gider. Yani `app_test.py`'de artık JS'te normal tek ters bölü (`\n`, `\'`) yazılmalı — ÇİFT YAZMA (`\\n`), aksi halde browser'a fazladan ters bölü gider (syntax hatası vermez ama görsel/mantıksal bozukluk olur, bkz. Rev-107). `app.py` (canlı, henüz bu değişikliği almadı) HALA normal (raw olmayan) string — orada eski kural (çift `\\n`/`\\'` gerekir) geçerliliğini koruyor. `app_test.py`'deki değişiklikler `app.py`'ye taşınırken bu `r'''` farkını da birlikte taşımayı UNUTMA — aksi halde `app.py`'ye kopyalanan tek-ters-bölülü JS, normal string altında yanlış işlenir (Rev-104/105'teki hatanın aynısı).

## KRİTİK — Retroaktif Oran Hatası: "O Anki Değer" Her Zaman İşlem Satırına Kilitlenmeli (Rev-107, 2026-08-02)
- **Genel kural (sadece puantaj değil, tüm modüller için geçerli):** Bir işlem/kayıt (puantaj günü, hakediş kalemi, sipariş satırı vb.) parent bir varlığın (işçi, malzeme, poz) O ANKİ değişken oranını (ücret/birim fiyat) referans alıyorsa, bu değer işlem KAYDEDİLDİĞİ ANDA o satıra kopyalanıp kilitlenmeli — hesaplama zamanında parent'tan CANLI okunmamalı. Aksi halde parent'ın değeri değiştiğinde (zam, fiyat güncellemesi) TÜM GEÇMİŞ kayıtlar sessizce yeniden hesaplanır.
- **Somut örnek:** `pythonanywhere/app.py` puantaj tablosunda `gunluk_ucret` sütunu vardı ama hiç yazılmıyordu — bakiye hesabı hep `isci.gunluk_ucret` (güncel) kullanıyordu. İşçiye zam yapılınca geçmiş tüm günler yeni ücretten hesaplanıyordu.
- **Çözüm deseni:** (1) INSERT'te o anki oranı satıra yaz. (2) UPDATE'te KOŞULSUZ ezme — `COALESCE(mevcut_deger, o_anki_deger)` ile sadece NULL/boş olanı doldur, kilitli değeri koru. (3) Hesaplama SQL'inde `SUM(miktar * COALESCE(satir.oran, parent.oran))` gibi PER-ROW çarpım kullan, `toplam_miktar * parent.oran` gibi toplu/agregat çarpım KULLANMA.
- **Eski (migration-öncesi) NULL kayıtlar:** `COALESCE(satir.oran, parent.oran)` fallback yeterli — veri kaybı riski sıfır. Kullanıcı "güncel değerle backfill et" isterse (bu proje Rev-107'de böyle seçildi), backfill UPDATE'i `init_db()` içine idempotent (`WHERE oran IS NULL`) olarak koy — ayrı bir tetikleme endpoint'i gerekmez, uygulama her başladığında otomatik çalışır ve NULL kalmayınca etkisiz kalır.
- **Kontrol listesi:** Yeni bir modülde "geçmişe dönük değişmemesi gereken bir tutar" görürsen (ücret, birim fiyat, kur, vergi oranı vb.) bu deseni uygula — canlı JOIN ile parent'tan okumak yerine işlem anında satıra kopyala.

## KRİTİK — GanttEngine Task Sınıfı Kullanımı (2026-03-19)

`app/core/gantt_engine.py` içindeki `Task.__init__` imzası:
```python
Task(task_id: int, ad: str, sure_gun: int, baslangic_tarihi=None,
     bitis_tarihi=None, ilerleme=0.0, metraj_kalem_id=None,
     aciklama="", milestone=False, kaynak="", wbs_kodu="",
     parent_id=None, renk="#3498db")
```

**Kesin Kurallar:**
- ❌ `Task(id=x, ...)` → YANLIŞ — `id` diye parametre YOK
- ✅ `Task(task_id=int(x), ...)` → DOĞRU
- ❌ `Task(oncul_ids=[...], ...)` → YANLIŞ — `oncul_ids` diye parametre YOK
- ✅ Task oluşturduktan sonra `task.predecessors.append((int(oncul_id), "FS", 0))` → DOĞRU
- ❌ `Task(kaynak=None, ...)` → YANLIŞ — `kaynak` tipi `str`
- ✅ `Task(kaynak=kaynak or "", ...)` → DOĞRU
- `task_id` **int** olmalı (str değil); `tasks` dict'i `int` key kullanır
- `predecessors` formatı: `List[Tuple[int, str, int]]` = `(task_id, dep_tipi, lag_gun)`
  - dep_tipi: `"FS"` | `"SS"` | `"FF"` | `"SF"`

**Yeni Task oluşturma şablonu:**
```python
tid = int(yeni_id)
task = Task(
    task_id=tid,
    ad=ad,
    sure_gun=sure_gun,
    baslangic_tarihi=baslangic,
    bitis_tarihi=bitis,
    kaynak=kaynak or "",
    ilerleme=0.0,
)
for oncul_id in oncul_listesi:
    task.predecessors.append((int(oncul_id), "FS", 0))
self._gantt_engine.tasks[tid] = task
```

**Kural:** Yeni Task kodu yazmadan önce `gantt_engine.py`'deki `Task.__init__` imzasını Read ile oku — parametre isimleri değişmiş olabilir.

## Gayrimenkul Kira Getirisi Sabitleri (2026-04-08)
- **Hata:** `kira_aylik = deger * 0.003 / 12` → yıllık %0.3 getiri, 269 yıl geri ödeme (10x hata)
- **Doğru:** Türkiye brüt kira getirisi bölgeye göre **%2.5–5/yıl**
  - m² < 30.000 TL → %4–5 (ucuz bölge, Arnavutköy/Esenyurt vb.)
  - m² 30k–60k    → %3.5–4.5 (orta bölge)
  - m² 60k–100k   → %3–4 (değerli bölge)
  - m² > 100k     → %2.5–3.5 (Beşiktaş/Kadıköy/Sarıyer vb.)
- **Konum:** `claude_engine.py` → `_arac_gayrimenkul_degerle()` kira getirisi bloğu
- **Formül:** `kira_aylik = deger * getiri_orani / 12` (yıllık oran / 12 = aylık)
